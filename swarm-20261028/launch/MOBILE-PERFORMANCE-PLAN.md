# Mobile performance plan — source-only audit

**Scope:** Read-only review of `game/` for the current public beta source. No game files changed, no browser profiling or gameplay run performed, and no performance improvement is claimed. This report distinguishes startup transfer/decode from sustained frame time. Device, browser, network, and physical-phone behavior remain unmeasured.

## Findings from source

- **The loading screen waits on many resources before play is marked ready.** `game/siempre-zombie.js:3060-3071` waits on the shared zombie body, fitted-character preload, physical-death data, weapon viewmodels, taco truck, RZR, viewmodel images, spin sheets, and shader compilation. `game/siempre-zombie.js:42-45` sets an estimated `LOAD.expect` of 33 MB, but progress only counts FileLoader requests and synthetic 1.5 MB completion entries; HTML image decoding and several TextureLoader requests are outside exact byte accounting.
- **Known local GLBs alone imply a substantial initial payload.** World `assets/world-lawn-v118-d7c4d3e9.glb` is 24,982,908 B (23.83 MiB); zombie body is 7,668,896 B (7.31 MiB); selected RZR is 8,847,848 B (8.44 MiB); taco truck is 9,686,220 B (9.24 MiB). That is about **48.8 MiB** before the six fitted head GLBs and six 2K body albedos. `game/distillery-world.js:21-45,164` loads world, several ground textures, the 1,344×1,344 surface texture, and environment HDR; `game/fitted-zombie-variants.mjs:18-28` preloads all six heads/body textures; `game/rzr6-loader.js:12-14` and `game/taco-truck.js:39` load their respective GLBs. The deployed beta HEAD requests returned 200 for a sample of these GLBs. `Content-Encoding` and `Content-Length` were absent; Cache-Control was `public, must-revalidate, max-age=0`. A HEAD response does not establish transfer size or time.
- **Large source-art PNGs appear in the repository, but their runtime use is not established by this audit.** `character-art.js` defines a loader but no game import/call was found. Do not count those originals as startup bytes without tracing actual browser requests.
- **Renderer defaults target visual quality.** `game/siempre-zombie.js:182-188` enables antialiasing, caps touch DPR at 1.5 (desktop 2), enables PCF soft shadows, and uses ACES tone mapping. Pixel work scales with DPR squared: 1.5 DPR is 2.25× the backing pixels of DPR 1; 2 DPR is 4×. The moon directional light uses 1,024² shadow maps for touch and 2,048² otherwise (`:308-314`); zombie meshes cast and receive shadows (`:140-141`), as do many props and vehicles.
- **The main loop continues rendering outside active play.** `game/siempre-zombie.js:3019-3059` schedules a RAF every frame and always renders. It updates particles, weapon views, truck, flickering lights, mist, HUD effects, distillery lighting, driver view, and boundary fog; title state also animates camera and weapon spins. Flicker updates call `Math.random()` each frame (`:3045`). During play, zombie/player/weapon updates and HUD work add to the frame (`:3023-3027`). This is a plausible sustained-FPS cost, but source inspection cannot rank its actual device impact.
- **Touch-control markup/styles are not an obvious heavy continuous cost.** `game/index.html:139-...` contains the control DOM and `game/mobile-hud.css` styles buttons/joystick; the touch controls are static DOM and event-driven CSS, with no evidence here that they dominate frame time. The in-game mobile joystick/button code should be profiled alongside the scene when measuring, not optimized speculatively.

## Ranked plan (measurement first)

1. **Establish separate baselines on real phones.** Use one lower-mid-range Android and one recent iPhone if available, record exact model/OS/browser, screen resolution, network, battery/thermal state, and beta revision. Capture cold-cache and warm-cache start-to-title-ready times and transferred bytes per request; then run a repeatable 5-minute gameplay route with representative waves, effects, and vehicle use. Record frame-time percentiles, missed frames, memory, and thermal drift. Keep startup/network and gameplay/frame metrics separate.
2. **Test the cheapest rendering variable first.** Compare current touch DPR cap 1.5 against 1.25 and 1.0 under the identical route, then compare shadow map/render settings as a separate run. Preserve visuals for each comparison. Choose only a change with repeatable frame-time improvement and acceptable image quality; do not combine changes before attribution.
3. **Audit eager loading using a request waterfall.** Identify which assets are needed before first playable state versus later encounters. Compare cold-cache downloaded bytes and decode/compile time against a deferred-load prototype in an isolated branch. Start with nonessential truck/vehicle/rare-character resources if they are not required at first play; preserve graceful loading before use. Validate that the loading meter reflects actual required bytes and does not reach ready early.
4. **Use frame traces to target the hot loop.** In device profiling, separate GPU time (resolution, soft shadows, transparent overdraw) from JS time (zombie animation/AI, per-frame HUD/style writes, particle/grass work, vehicle updates). Only then trial a small targeted change such as lower touch shadow-map cost, reduced offscreen animation, or less frequent noncritical HUD/flicker updates. Re-run the same route and visual comparison after each isolated change.

## Practical acceptance target for a mobile pass

- On the agreed lower-mid-range phone, sustain **at least 30 FPS** through the representative 5-minute route, with **95th-percentile frame time at or below 33 ms** and no sustained thermal collapse; target 60 FPS on recent phones where the device/browser supports it.
- On a documented 10 Mbps network, target **first playable within 10 seconds on cold cache** and **≤20 MiB transferred before first play**; later-needed assets may stream before they are used. These are proposed product targets, not measured results. Revise them if actual audience device/network data says they are unrealistic.
- No blocking missing assets, material visual regressions, broken mobile controls, or new long pauses when a deferred asset is first needed.

**Limits / unknowns:** No physical-phone, browser profiler, gameplay, cold-cache network, device matrix, or deployed transfer-volume measurement was available in this bounded source audit. Local file sizes are exact; compressed transfer bytes and runtime frame rate are unknown. The canonical beta HEAD sample only verified successful responses and cache headers.
